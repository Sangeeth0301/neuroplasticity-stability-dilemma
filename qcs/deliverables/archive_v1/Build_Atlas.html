01 — Repository

The complete folder and file structure

One installable package (src/qcs/), thin CLI scripts that only parse arguments and call into it, and a strict separation between code, configs, data, and runs. Nothing under runs/ is ever edited by hand; everything there is regenerable from a config plus a seed.

Why scripts are thin

Every script is ≤ 40 lines: parse args, load config, call one function in src/qcs/, write outputs. Logic in a script is logic that cannot be unit-tested, reused from a notebook, or called from a sweep.

Why viz/style.py exists

One module owns the palette, fonts, figure sizes, and the transparent-background save path. Forty-five figures with per-file styling become forty-five inconsistent figures; this is the cheapest possible fix and it must exist from day one.

03 — Visualization contract

Rules that make forty-five figures usable instead of forty-five files

Emission rules

  • Every figure has a stable id V01…V45 and a stable filename V17_grad_variance_vs_depth.png. Ids never get reused or renumbered.
  • Figures are written to runs/<run_id>/figs/, never to a global folder. Curation into figs/ is a manual, deliberate act.
  • Every figure is regenerable from metrics.jsonl + checkpoints by make figures. If a plot needs data that was not logged, log it — do not compute it inside the plotting code.
  • Each figure's caption embeds the run id, git hash and seed. A screenshot with no provenance is worthless three weeks later.
  • Every figure is saved as PNG (dpi 130, transparent) and SVG for the write-up.

Reading rules

  • Each figure spec states a pass read and a fail read before it is ever generated. A plot you do not know how to fail is decoration.
  • Comparison figures always overlay the quantum and classical arms on identical axes — never two separate plots side by side at different scales.
  • Anything measured across the task sequence uses the same x-axis (task index) so figures can be stacked and read together.
  • Colour is fixed by role: classical/stability teal, quantum/plasticity magenta, oracle grey dashed. Never re-map.

04 — Live results

What your dataset actually looks like as qubits

These three figures are not mockups. They were produced by viz_stage_demo.py, a self-contained numpy/scipy statevector simulation of the exact pipeline described in the blueprint: a 1024-dimensional feature vector built from the four structural blocks, normalised onto the unit sphere, amplitude-encoded into ten qubits, evolved through eight brickwall layers of general SU(4) gates, and read out as a single ⟨Z₉⟩. Run it yourself — it takes about a minute and needs nothing but numpy, scipy and matplotlib.

The demo already caught a real bug class

Look at the bottom-left heatmap: nearly all the amplitude mass sits in the last few rows — the relational block ρ — and the participation ratio is only 61 of 1024 basis states. Because the interaction and relational blocks were built at a larger scale than the projections, normalisation handed them most of the probability, and the query/candidate blocks were squeezed toward vacuum. In a real run, that circuit would be scoring almost entirely on recency and graph features while ignoring semantics.

The fix, and it belongs in encode/assemble.py: normalise each block to a target share of the total norm (e.g. 0.35 / 0.35 / 0.20 / 0.10) before the global L2 step, and log the per-block norm fractions as figure V13b every run. This is exactly the failure the S6 warning in the blueprint predicted — and it is invisible in the code, visible in one plot.

How to use these two figures during the build

The entanglement-vs-cut panel is your ansatz health check: if the curves stay flat and low as depth grows, the gate pattern is wrong (usually a pairing bug that leaves qubits disconnected). The readout-separation histogram, re-plotted every 50 tasks, is your single most informative training diagnostic — you want to watch those two distributions pull apart and stay apart, which is precisely what preserved plasticity looks like in this system.

Read this one carefully — and note one correction

  • Correction (2026-08-20). An earlier version of this page reported the global observable as a measured barren plateau falling fifteen orders of magnitude. That figure was wrong: the code computed Π_q ⟨Z_q⟩, a product of marginals, which decays exponentially in N by construction and is not the global observable at all. With the correct parity expectation ⟨Z⊗Z⊗…⊗Z⟩ = Σ_j (−1)^popcount(j)|ψ_j|², a 10-qubit circuit at depths ≤ 16 shows no plateau — variance stays around 2e−4, comparable to the local readout. Both the standalone demo and the built repository (figure V17) now agree on this.
  • The light cone is real and reproduces exactly. Local-observable variance is ~1e−31 (numerically zero) at depths 1–4, then jumps to 1e−4 at depth 6 and stays flat through depth 16. A parameter acting on qubits (0,1) physically cannot influence q₉ in fewer than ⌈N/2⌉ brickwall layers, so its gradient is not small — it is identically zero. The repository computes this depth from the gate topology (light_cone_depth(10, 9) = 5) and Config.validate() refuses to load a shallower circuit.
  • The design consequence is unchanged: L ≥ 6 is a hard floor at N=10 with a single-qubit readout, and the local observable remains the default — now justified by the light cone and by standard barren-plateau theory for deep global-observable circuits, rather than by our own measurement.
